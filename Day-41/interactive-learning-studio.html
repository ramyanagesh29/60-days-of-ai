Arrays: Contiguous Memory

Where the data lives, and why that single fact explains almost everything about how arrays behave.

What an array actually is

An array is a block of memory cells sitting right next to each other, all the same size, holding the same type of value. The array variable itself just remembers one thing: the base address — where the block starts.

Every other position is computed, not stored. To find element at index i, the computer does simple arithmetic:

address(i) = base_address + (i × element_size) // Example: base = 0x00, element_size = 4 bytes // address(0) = 0x00 + (0 × 4) = 0x00 // address(2) = 0x00 + (2 × 4) = 0x08
Analogy — a street of identical houses: imagine houses numbered 100, 104, 108, 112 — evenly spaced, same size, on one street. If you know house 100 is the start and each house is 4 meters wide, you can walk directly to house #7 without visiting the ones before it. That's exactly how array[7] works: direct math, not a walk.

Diagram: index → address

Static vs. Dynamic Arrays

A static array has a fixed size decided at creation (e.g. C's int arr[10]). A dynamic array (JavaScript arrays, Python lists, Java ArrayList) appears to grow freely, but under the hood it's still a fixed-size block — when it fills up, it silently allocates a new, bigger block (usually double the size), copies everything over, and frees the old one.

Common misconception: "Dynamic arrays can grow forever without cost." In reality, that resize-and-copy step is O(n) when it happens — it's just rare enough (doubling means it happens ~log(n) times) that the average cost per insertion stays O(1). This is called amortized O(1), not literally O(1) every time.

✏️ Practical Exercise

You have array [5, 8, 2, 9, 1]. Write out, step by step, what happens internally (which elements move, and where) when you insert 7 at index 2. Then state the final array and its Big-O cost.

Key Takeaways — Module 1

  • Arrays store elements contiguously; index access is pure arithmetic → O(1).
  • Dynamic arrays resize by doubling and copying — amortized O(1) insert at the end.
  • Inserting/deleting anywhere but the end costs O(n) due to shifting.
  • Arrays are cache-friendly: contiguous memory means fast sequential reads.

What a linked list actually is

A linked list is a chain of independent nodes. Each node holds two things: a value, and a pointer (memory address) to the next node. There's no shared block of memory — nodes can live anywhere, scattered across memory, connected only by these pointers.

struct Node { value: any next: Node | null } // head → [12|•]→[7|•]→[54|•]→[3|null]
Analogy — a treasure hunt: each clue doesn't tell you a location number; it tells you where to find the next clue. You can't skip to clue #4 — you must follow clue 1 → 2 → 3 → 4 in order. That's a linked list: no shortcuts, only "follow the pointer."

Diagram: singly linked list

Singly vs. Doubly vs. Circular

Singly linked list: each node points forward only. Simple, lower memory, but you can't walk backward.

Doubly linked list: each node has next AND prev. Enables backward traversal and O(1) deletion when you already hold the node — at the cost of extra memory per node.

Circular linked list: the last node points back to the head instead of null. Useful for round-robin scheduling, playlists on loop, or turn-based games.

Common misconception: "Linked lists are always better for insertion because it's O(1)." Insertion is only O(1) if you already have a reference to the node right before the insertion point. Finding that node in the first place is O(n) — so inserting "at position 500" is still effectively O(n) overall.

✏️ Practical Exercise

You maintain a music queue as a singly linked list: head → SongA → SongB → SongC → null. A user wants to remove "SongB". Describe exactly which pointer(s) change, and why you need a reference to SongA (the node before SongB) to do it in O(1).


Expected reasoning: SongA.next currently points to SongB. To remove SongB, set SongA.next = SongB.next (which is SongC). SongB is now unreferenced and gets garbage collected. This is O(1) only because we already had SongA — without it we'd need O(n) to find it by walking from head.

Key Takeaways — Module 2

  • Linked lists trade random access for flexible, cheap insertion/deletion at known points.
  • Doubly linked lists add backward traversal at the cost of extra memory.
  • Circular lists remove the "end" — last node points back to head.
  • O(1) insert/delete claims only hold if you already have the relevant node reference.

Two-Pointer Technique (Arrays)

Instead of nested loops (O(n²)), use two indices moving toward or alongside each other to solve problems in O(n).

// Is array a palindrome? e.g. [1,2,3,2,1] let left = 0, right = arr.length - 1; while (left < right) { if (arr[left] !== arr[right]) return false; left++; right--; } return true;
Analogy: two people starting at opposite ends of a bookshelf, walking toward each other, checking that each pair of books matches — meeting in the middle instead of one person walking the whole shelf twice.

Sliding Window (Arrays)

Maintain a "window" (subarray) that expands and contracts as you scan once through the array — great for "max/min subarray of size k" or "longest substring" problems.

Fast & Slow Pointers (Linked Lists)

Two pointers traverse a linked list at different speeds (slow moves 1 step, fast moves 2). If the list has a cycle, they will eventually meet. If it doesn't, fast reaches null first.

function hasCycle(head) { let slow = head, fast = head; while (fast && fast.next) { slow = slow.next; fast = fast.next.next; if (slow === fast) return true; } return false; }
Analogy — a race track: a runner twice as fast as another, on a circular track, will always eventually lap the slower one. On a straight track (no cycle), the fast runner just finishes first — they never "meet."

Reversing a Linked List

A classic mastery-check: reverse all the next pointers so the list points the other way, using three tracking pointers (prev, current, next).

function reverse(head) { let prev = null, curr = head; while (curr) { let nextNode = curr.next; curr.next = prev; prev = curr; curr = nextNode; } return prev; // new head }
Common misconception: "You can reverse a list by just relabeling head and tail." Nodes don't know they're "first" or "last" — only pointers define order. Every single next pointer must be individually flipped.

✏️ Practical Exercise

Given array [3, 1, 4, 1, 5, 9, 2, 6], use the sliding window technique (mentally) to find the maximum sum of any 3 consecutive elements. Show each window's sum as it slides.


Expected reasoning: Windows: [3,1,4]=8, [1,4,1]=6, [4,1,5]=10, [1,5,9]=15, [5,9,2]=16, [9,2,6]=17. Max = 17. Efficient approach: subtract the outgoing element and add the incoming one each slide, rather than re-summing — O(n) total instead of O(n×k).

Key Takeaways — Module 3

  • Two-pointer and sliding-window patterns turn O(n²) array problems into O(n).
  • Fast/slow pointers detect cycles in linked lists without extra memory (Floyd's algorithm).
  • Reversal requires tracking three pointers and flipping every link individually.
  • These patterns are the building blocks of most array/linked-list interview questions.

Choosing the right structure: a decision framework

Ask three questions:

  1. Do I need random access by index? → Array wins (O(1) vs O(n)).
  2. Do I insert/delete frequently at the front or middle? → Linked list wins (no shifting).
  3. Do I care about memory locality / cache performance? → Array wins (contiguous = fast CPU cache hits); linked lists scatter memory and cause "pointer chasing," which is slow on real hardware even though Big-O looks favorable.
Common misconception: "Big-O is the whole story." In practice, arrays often outperform linked lists even for operations where linked lists have better Big-O, because CPU caches love contiguous memory. Big-O ignores constant factors and hardware reality — always sanity-check with real-world context.

Case study: designing an LRU Cache

A Least-Recently-Used cache needs: O(1) lookup by key, and O(1) move-to-front / evict-oldest. Neither structure alone is enough:

  • A hash map gives O(1) lookup by key.
  • A doubly linked list gives O(1) reordering (move a node to the front) and O(1) removal of the tail (oldest item) — because you already have direct node references from the hash map.

Combined: hash map stores key → node reference; doubly linked list maintains usage order. This is exactly how production LRU caches (e.g. in Redis-like systems) are built.

✏️ Practical Exercise

You're designing a text editor's "undo" feature. Would you use an array or a linked list for the undo stack? Justify your choice using the three-question framework above, and describe what operations you'd need.


Expected reasoning: Either works reasonably, but a dynamic array (used as a stack, push/pop only at the end) is usually preferred in practice: no random access needed mid-stack, operations are O(1) amortized at the end for arrays too, and arrays have better cache locality for the "replay all undo steps" scan. A linked list is also valid if memory is fragmented/unpredictable and you want to avoid resize-copy pauses.

Key Takeaways — Module 4

  • Use a 3-question framework: random access? frequent front/middle edits? cache locality?
  • Real systems often combine structures (e.g. hash map + doubly linked list for LRU cache).
  • Big-O doesn't capture hardware reality — contiguous memory usually wins in practice.
  • Matching structure to access pattern is the core skill of data structure design.

Bring together everything: memory layout, complexity trade-offs, and pointer manipulation.

Challenge: Detect and Remove a Cycle

You're given a singly linked list that may contain a cycle (a bug elsewhere in the codebase caused a node's next to accidentally point back to an earlier node). Your task, in plain-English pseudocode:

  1. Detect whether a cycle exists (which technique from Module 3 applies?).
  2. If a cycle exists, find the exact node where it begins.
  3. Break the cycle by setting the appropriate node's next to null.


Model solution (Floyd's Cycle Detection, extended):
1) Use fast/slow pointers — if they meet, a cycle exists.
2) To find the start: reset one pointer to head, keep the other at the meeting point, then move both one step at a time — they meet exactly at the cycle's starting node (a property of the math behind Floyd's algorithm).
3) Once you have the start node, traverse from it until node.next === start, then set that node's next = null.
Overall: O(n) time, O(1) space — no extra memory needed, unlike a hash-set approach which would use O(n) space.

Summary Notes

Arrays are contiguous memory with O(1) index math but O(n) mid-insertions; linked lists are scattered nodes connected by pointers, giving O(1) edits at known points but O(n) access. Amortized doubling makes dynamic array appends cheap on average. Two-pointer, sliding-window, and fast/slow-pointer patterns solve most classic problems in O(n). Real systems (like LRU caches) often combine both structures to get the best of each. Choosing between them is a trade-off exercise, not a "one is better" question — and real hardware cache behavior matters as much as Big-O.
